== 38.1  proof that Python's own hash() is unusable on screen ==
five fresh interpreters, default (randomised) seed, printing hash('ab')%10:
  hash('ab')%10 -> 2   hash('cd')%10 -> 0   (crc32: 5, 4)
  hash('ab')%10 -> 0   hash('cd')%10 -> 4   (crc32: 5, 4)
  hash('ab')%10 -> 4   hash('cd')%10 -> 0   (crc32: 5, 4)
  hash('ab')%10 -> 8   hash('cd')%10 -> 3   (crc32: 5, 4)
  hash('ab')%10 -> 3   hash('cd')%10 -> 3   (crc32: 5, 4)
distinct values seen for hash('ab') % 10: ['0', '2', '3', '4', '8']
=> crc32 is identical in all five runs; hash() is not. Screen must use the deterministic one.
with PYTHONHASHSEED=0 the same line is stable at: hash('ab')%10 = 1, hash('cd')%10 = 1
=> pinning the seed makes Python's own hash reproducible (and here it even collides, in slot 1),
   but a render that forgets the env var silently changes the number. Do not use it on screen.

== 38.6  open addressing: SAME function, SAME m = 4, linear probing ==

both strategies begin from the identical collision the script names: 'ab' and 'cd' both
want slot 3. Chaining stacks them there. Open addressing sends 'cd' probing 3 -> 0.
